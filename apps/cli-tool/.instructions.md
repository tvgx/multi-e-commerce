# E-commerce CLI Tool - Copilot Instructions

**Version 1.0** | Applies to: Phases 1-4 Complete | Last Updated: April 6, 2026

Guidance for GitHub Copilot when assisting with the E-commerce CLI tool across all phases.

---

## Core Principles

### 1. Security First
- Always mention `--dry-run` before risky operations
- Suggest backup creation before shop deletion
- Warn about production environment implications
- Remind about audit trail logging
- Reference AGENTS.md for permission checks

### 2. Production Safety
- Preview changes with `--dry-run` first
- Require explicit confirmation for destructive ops
- Auto-backup before mutation commands
- Suggest JSON output (`--json`) for scripting
- Validate input before API calls

### 3. Automation-Ready
- Flag-based CLI (never use interactive prompts)
- JSON output support for all commands
- Stateless operations (no local state between runs)
- Idempotent when possible
- Parallel-friendly (no file locking)

## Command Assistance by Category

### Shop Management

**When suggesting CREATE:**
```python
# Always include owner email and template
python main.py shop create \
  --name "Store Name" \
  --domain example.com \
  --owner-email owner@example.com \
  --template fashion

# Mention audit logging benefit
# → Automatically logged: SHOP_CREATED event
```

**When suggesting DELETE:**
```bash
# ALWAYS suggest dry-run first + backup
python main.py shop delete <shop-id> --dry-run
python main.py backup create <shop-id>
python main.py shop delete <shop-id> --force

# Warn: "This creates auto-backup. Rollback available with:
#       python main.py backup rollback <shop-id>"
```

**When suggesting UPDATE:**
```bash
# Preview first, then apply
python main.py shop update <shop-id> --name "New" --dry-run

# Mention risk level
# → MEDIUM risk: Creates audit trail, can rollback via backup
```

### Backup Operations

**When suggesting RESTORE:**
```bash
# Always show available backups first
python main.py backup list <shop-id>

# Preview before restoring
python main.py backup restore <shop-id> --dry-run

# Then execute
python main.py backup restore <shop-id>

# Warn: "Data loss possible. Always verify backup timestamp."
```

**When suggesting CLEANUP:**
```bash
# Only old backups (mention retention policy)
python main.py backup delete <shop-id> <timestamp> --force

# Suggest: "Backups retained for 30 days by default.
#          Old backups auto-cleaned monthly."
```

### Batch Operations

**When suggesting BATCH CREATE:**
```bash
# Show CSV/JSON format first
cat sample.csv
# Output:
# name,domain,owner_email,template
# Shop1,shop1.com,owner1@example.com,fashion

# Key flags to mention:
# --dry-run: Preview first
# --parallel 5: Concurrency
# --continue-on-error: Resilience
# --json: Machine-readable output

python main.py batch create shops.csv --dry-run
python main.py batch create shops.csv --parallel 10
```

**When suggesting PARALLEL PROCESSING:**
```python
# Mention performance/resource tradeoffs:
# Workers | Time | Memory | CPU
# 5      | 10m  | 300MB  | 500m
# 10     | 5m   | 600MB  | 1000m
# 20     | 2.5m | 1.2GB  | 1.5000m

# Suggest starting with 5, scale up if stable
```

### Health & Monitoring

**When suggesting HEALTH CHECK:**
```bash
# Full report for troubleshooting
python main.py health check <shop-id> --full

# Mention score interpretation:
# 90-100%: Ready for production
# 80-89%: Minor issues to address
# <80%: Should fix before going live

# Auto-fix option (be cautious):
python main.py health check <shop-id> --auto-fix
# Warn: "Auto-fix will modify shop data. Always backup first."
```

### Environment Sync

**When suggesting SYNC:**
```bash
# STRICT: Enforce environment hierarchy
# dev → acceptance → staging → prod (can't skip or reverse)

# Always preview first
python main.py sync config <shop-id> --from dev --to acceptance --dry-run

# Show what changes
# Then execute with backup
python main.py sync config <shop-id> --from staging --to prod

# Warn: "Backup auto-created before sync. Rollback with:
#       python main.py backup rollback <shop-id>"
```

## Error Messages & Troubleshooting

### Common Errors

| Error | Solution |
|-------|----------|
| `AuthenticationError` | Check: `config --show`, re-login |
| `ShopNotFoundError` | Check: `shop list`, verify shop-id |
| `ValidationError` | Check: Input format, see `shop create --help` |
| `APITimeout` | Check: Network, increase timeout in config |
| `DiskSpace` | Check: `backup list`, cleanup old backups |

### When Suggesting Fixes

```bash
# Always verify first
python main.py config --show  # Check auth status
python main.py audit view --status failed  # See recent failures

# Then suggest fix with context
# "Failed because: [specific reason from error]
#  Solution: [action with example command]
#  Prevention: [future avoid with flag/setting]"
```

## Best Practices to Suggest

### Development Workflow

```bash
# 1. Start with dry-run
python main.py batch create shops.csv --dry-run

# 2. Check audit trail to understand system
python main.py audit view --json

# 3. Create backup before any mutation
python main.py backup create <shop-id>

# 4. Execute with monitoring
python main.py batch create shops.csv --json | tee results.json

# 5. Verify results
python main.py audit view --action batch
```

### Production Checklist

- [ ] All commands tested in staging first
- [ ] Backups verified before risky ops
- [ ] Health check passed (score >= 80)
- [ ] Audit trail reviewed
- [ ] Team approval obtained
- [ ] Rollback plan prepared
- [ ] Change ticket created

## Code Examples to Provide

```bash
# 1. Prepare CSV

name,domain,owner_email,template

# 3. Execute with good parallelism

```

### Example 2: Safe Production Promotion

```bash
# 1. Check health in staging
python main.py health check <shop-id> --full

# 2. Preview sync
python main.py sync config <shop-id> --from staging --to prod --dry-run

# 3. Create backup
python main.py backup create <shop-id>

# 4. Execute sync
python main.py sync config <shop-id> --from staging --to prod

# 5. Verify in production
python main.py health check <shop-id>
```

### Example 3: Disaster Recovery

```bash
# 1. Identify the issue
python main.py health check <shop-id> --full

# 2. Check audit trail
python main.py audit view --shop <shop-id> --status failed

# 3. List available backups
python main.py backup list <shop-id>

# 4. Restore from backup
python main.py backup restore <shop-id> --timestamp 20260406_120000

# 5. Verify recovery
python main.py health check <shop-id>
```

## Role-Based Guidance

### For Developers

When a developer is coding:
- Focus on `--dry-run` and local testing
- Suggest `docker-compose` for full stack
- Emphasize `--json` output + scripts
- Avoid production commands (redirect to ops)

Example: "You're testing shop creation. Use `docker-compose exec cli` to test against local services."

### For Operations Engineers

When an ops person is running:
- Suggest batch operations over single commands
- Emphasize parallel processing
- Focus on monitoring & health
- Provide runbook patterns

Example: "For 500 shops, use batch with 20 workers: takes ~3 minutes vs 2 hours manually."

### For Platform Admins

When a platform admin is working:
- Include emergency procedures
- Emphasize audit trail
- Suggest automation (CronJobs, GitHub Actions)
- Focus on SLA/compliance

Example: "This creates auto-backup due to role. Check audit with: `audit view --json > compliance.json`"

## Flags & Options Reference

### Common Flags

```
--dry-run           Preview changes without executing
--json              Machine-readable output
--force             Skip confirmation (admin only)
--parallel N        Parallel workers (batch ops)
--continue-on-error Skip failed items
--full              Detailed output (health, audit)
--json              JSON format for scripting
--shop-id <ID>      Scope to specific shop
--from, --to        Environment sync
--timestamp <TS>    Specific backup timestamp
```

## Anti-patterns to Avoid

```
❌ Suggesting: python main.py shop delete <id>
✓ Instead: Suggest --dry-run first, mention auto-backup

❌ Suggesting: Manual backups for each shop
✓ Instead: Suggest batch operations or CronJobs

❌ Suggesting: Direct database queries
✓ Instead: Use CLI commands (audit trail better)

❌ Suggesting: Skipping dry-run in production
✓ Instead: Always preview first, especially for sync

❌ Suggesting: Manual environment sync
✓ Instead: Use sync command with enforced hierarchy
```

## Quick Decision Trees

### "I want to create shops"

```
Many shops?
├─ YES → Use batch create (CSV/JSON)
│        Suggest --parallel, --dry-run first
└─ NO  → Use shop create or wizard
         Suggest --dry-run first

Single shop?
├─ Interactive setup → wizard start
├─ Scripted → shop create with all flags
└─ Bulk import → batch create
```

### "I want to back up shops"

```
Frequency?
├─ One-time → backup create <shop-id>
├─ All shops → K8s CronJob (auto 2 AM)
└─ Manual → backup list, backup create

After backup?
├─ Restore → backup list, backup restore
├─ Rollback → backup rollback
└─ Cleanup → backup delete (auto handles 30 days)
```

### "I want to sync config"

```
Environments?
├─ dev → acceptance  → sync config --from dev --to acceptance
├─ acceptance → staging → sync config --from acceptance --to staging
├─ staging → production → sync config --from staging --to prod (needs approval)
└─ Other → "Invalid: Can't skip or reverse hierarchy"

Preview first?
├─ YES → Add --dry-run (shows differences)
├─ After preview → Remove --dry-run to execute
└─ Backup auto-created before sync
```
